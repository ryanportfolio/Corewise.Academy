<p class="lede">
The hype version of a company knowledge base is a glowing 3D brain floating on
screen. The useful version has no picture at all. It is a system that reads
everywhere your team already writes, the chat threads, the wiki, the code, and lets
anyone ask a plain question and get an answer drawn from all of it. Nick Saraev
walked through one that a chip company, Cerebras, runs internally and <a
href="https://www.cerebras.ai/blog/how-we-built-our-knowledge-base">wrote up in
detail</a>, fielding about 15,000 questions a day.
</p>

## <span class="sec-no">01</span>Put the answer up front

Retrieval augmented generation is just fetching the facts, and the whole game is
finding the right facts to put there, and a knowledge base is the machine that finds
them. This is the automatic version of what you do by hand when you <a
href="/guides/brief-the-model/">Brief the model like a brilliant new hire</a>.

## <span class="sec-no">02</span>Gather what your team knows

A knowledge base is only as good as what you feed it, so feed it where the knowledge
already lives. Slack messages, the wiki of checklists and onboarding pages, the code
and its history, and any database of numbers you track.

## <span class="sec-no">03</span>Store more than the raw text

Dumping the raw text in is where most knowledge bases stay mediocre. The good ones
label each item as they store it. A chat thread does not go in as a wall of text: a
model reads it first and attaches who spoke, when, what they were asking, and how it
resolved, the way a photo carries the time and place it was taken.

Those labels let the knowledge base weight what it finds. A founder's message from a
minute ago should count for more than a junior's note from three years back, and a
question about last week's seminar should surface last week's, not all of them
equally. Weighting by recency and source is the difference the hype visualizations
hide.

It is also why document count is a weak measure of quality. Nick's knowledge base
held about 640 items and Cerebras holds hundreds of thousands, yet the one that
answers well is the one that pulls the few most relevant items.

## <span class="sec-no">04</span>Match on words and on meaning

When a question comes in, the knowledge base has to find the right saved item, and
matching on meaning alone is not enough. Cerebras tried that first and it fell short,
so it now runs two kinds of match together.

Exact word matching catches an error string, a host name, or a flag someone pasted
in, where the precise characters are the whole point. Meaning matching catches the
question worded nothing like the answer: someone asks why a restore hangs, the saved
thread says the checkpoint stalls on the mount, and the two share no words at all.
Run both, let the newer answer win a tie, and each one covers the other's blind spot.

## <span class="sec-no">05</span>Build it with a coding agent

You do not need a specialist to wire this up. Nick built his by pasting the
company's write-up into a coding agent and asking it to build the ingestion
pipelines, the plumbing that pulls data in, for his Slack, email, and GitHub. The
agent logs into each account and stands up the connection. When it needs a
credential, it tells you the steps: open the API, do the one-time login. Budget five
to ten minutes per source.

You supply the understanding of how the data should flow; the agent supplies the
wiring. His finished knowledge base, asked the same twenty questions with and
without it, answered seventeen with evidence and zero without. A knowledge base is
the team-sized version of what one agent gets when you <a
href="/guides/give-your-agent-a-memory/">Give your agent a memory</a>: recall that
outlives the session.

<Exercise>
1. Pick one source your team already uses: a Slack or Discord channel, an email
   inbox, or a single GitHub repo.
2. Open a coding agent and describe the source and what you want: pull each item,
   label it with who, when, and why, and store it so you can search it both by
   meaning and by exact words.
3. Ask the agent how to connect that source (the API and the one-time login), then
   let it build the pipeline. Give it five to ten minutes.
4. Run the same handful of real questions with and without the knowledge base, and
   count how many it answers with evidence.
</Exercise>
