<p class="lede">A dashboard can run without errors and still count draft orders as accepted orders. Tell the coding agent which orders to count, then check the total against sample records.</p>

Developer Matt Pocock found that detailed specifications were not enough to keep his video editor easy to change. In Nate Herk's interview [Matt Pocock: What to Learn Instead of AI Automation in 2027](https://www.youtube.com/watch?v=Z8lf5oWKfj0), he describes improving the code and giving the agent ways to test it.

## <span class="sec-no">01</span>Answer the business questions

Ask the agent to interview you before it builds the feature. Tell it what you want the app to do and why, as described in [Brief the model like a brilliant new hire](/guides/brief-the-model/).

Pocock [recommends follow-up questions to find missing requirements](https://www.youtube.com/watch?v=Z8lf5oWKfj0&t=1021s). Anthropic also [recommends an interview before larger features](https://code.claude.com/docs/en/best-practices#let-claude-interview-you). Ask the person responsible for the work about decisions you cannot make yourself.

For the order dashboard, answer:

- Which orders should the total include?
- Who may see customer details?
- What should the user see when a record is incomplete?
- Will this run locally or on a server?
- Which sample orders will we use, and what total should they produce?

You will [discover more requirements while building](https://www.youtube.com/watch?v=Z8lf5oWKfj0&t=1107s). Write down unanswered questions and update the plan as you resolve them. [Power start sessions with /enhance-prompt](/guides/power-start-sessions-with-enhance-prompt/) covers having the agent read back the request before starting work.

If the agent uses an unfamiliar term, ask it to explain the term and cite the documentation. Read that source yourself. Pocock [uses teaching sessions to prepare for reading primary sources](https://www.youtube.com/watch?v=Z8lf5oWKfj0&t=457s); [Learn a work skill with AI](/guides/learn-a-work-skill-with-ai/) covers checking what you learned.

## <span class="sec-no">02</span>Use the business's own terms

If the people handling orders call an order "accepted," use that name in the app and code. Switching between "accepted," "approved," and "confirmed" makes it hard to tell whether those words describe the same state.

Pocock [borrows this practice from domain-driven design](https://www.youtube.com/watch?v=Z8lf5oWKfj0&t=1439s), where it is called **ubiquitous language**. The people using and building the software agree on what its terms mean. Microsoft's [domain-analysis guidance](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis) notes that the same word may mean something different in another part of the business. Using a shared vocabulary does not require the microservices architecture discussed in that documentation.

A glossary for the dashboard might be:

| Term | Agreed meaning | How the dashboard treats it |
| --- | --- | --- |
| Draft order | A saved request awaiting acceptance | Appears in the review queue, excluded from accepted-order totals |
| Accepted order | A request the business has agreed to fulfill | Counted once when accepted, even if payment is pending |
| Paid order | An accepted order whose payment has cleared | Included in accepted-order totals; payment shown as a separate status |

Confirm the glossary with the person responsible for orders. Then ask the agent to find any names in the code or interface that conflict with those definitions. Record separate definitions for departments that use the same word differently, and agree which definition the dashboard uses for each department's records.

## <span class="sec-no">03</span>Keep the code easy to change

Pocock [tried spec-driven development for months](https://www.youtube.com/watch?v=Z8lf5oWKfj0&t=1654s) in his custom video editor. He kept updating detailed specifications and asking agents to produce code from them, but reports that the code got worse. He then focused on making the code easier to change.

Pocock is describing his own workflow. Anthropic's interview guidance still recommends writing a specification. Keep the agreed requirements, and check that the app follows them after each change.

For the dashboard, ask the agent to show the code that decides whether an order counts as accepted. When that rule changes, check the new count and rerun the existing checks for drafts and paid orders. If a small rule change requires edits in many unrelated files, ask the agent to explain why each file must change.

[Improve your Claude Code workflow](/guides/improve-your-claude-code-workflow/) covers checking code against stale project notes. When a business rule changes, update its definition and the checks that use it alongside the code.

## <span class="sec-no">04</span>Let the agent run the app

Make sure the agent can start the app and use the interface. Pocock [reports better results after making his video editor runnable by the agent](https://www.youtube.com/watch?v=Z8lf5oWKfj0&t=1991s). Dependencies, including a local recording application, had made browser access difficult. Once he resolved those problems, the agent could click through the editor and take screenshots.

Anthropic's [verification guidance](https://code.claude.com/docs/en/best-practices#give-claude-a-way-to-verify-its-work) recommends tests, builds, and screenshot comparisons. Match the check to what the app should do:

| Requirement | Evidence to inspect |
| --- | --- |
| Drafts stay out of accepted-order totals | Known draft and accepted records, with the expected count |
| An invalid record gets a useful error | The invalid input and the message shown in the running interface |
| A rule change leaves other features working | Checks for the new rule and existing checks for the other order states |
| The agent can run the app locally | Required services started; any blocked checks recorded |

Decide which checks must pass before accepting the work, as described in [Give your coding agent a finish line](/guides/give-your-coding-agent-a-finish-line/). Record any check the agent could not run.

Pocock [uses Opus 5.5 at medium effort](https://www.youtube.com/watch?v=Z8lf5oWKfj0&t=1925s). He reports faster replies and lower token use in his setup, where the agent has checks it can run. His results do not establish which setting will work best for your task.

Anthropic's [effort documentation](https://code.claude.com/docs/en/model-config#choose-an-effort-level) describes a tradeoff between token use and capability. Each model has its own effort scale, so the same level name can behave differently. Compare settings on the same task, run the same checks, and include the time you spend correcting mistakes. [Recheck your model choices each release](/guides/recheck-your-model-choices-each-release/) covers that comparison.

## <span class="sec-no">05</span>Show the business rule working

Build a prototype around a rule the client cares about. Pocock [suggests building something that reflects the client's business](https://www.youtube.com/watch?v=Z8lf5oWKfj0&t=1268s). He already had a large audience when he freelanced and says he has not competed for contracts. His experience does not establish how to win contracts against other bidders.

For the dashboard, show the client which orders appear in the total and which are left out. Explain what you checked and which questions still need answers. Before customers use the app, check access permissions and rerun the checks with the required services in the environment where it will run.

## <span class="sec-no">06</span>Try one feature locally

Build the first version with sample orders before connecting it to customer data. Pocock [recommends starting with ordinary, measurable work](https://www.youtube.com/watch?v=Z8lf5oWKfj0&t=2413s). Watch the agent work, inspect its changes, and learn how to stop it before allowing larger tasks or unattended runs. [Delegate to your agent in stages](/guides/delegate-to-your-agent-in-stages/) covers expanding that access.

Use this original prompt for the first trial:

```text
I want a local prototype of [one business task] using sample data. Read the existing code before editing. Ask me what the user needs to do, what the business terms mean, who may use the feature, and what should happen when something goes wrong. Wait for any answers you need before building.

Write a short glossary. List unanswered questions separately. Propose one feature, with sample inputs and expected results. Return the plan for review.

After I approve the plan, build that version and demonstrate it in the running app. Show the code that implements the business rule. Run the agreed checks and report any you could not run. When I change a requirement, update the affected code, glossary, and checks, then check the new result and rerun the existing checks.

Keep this trial local, preserve unrelated files, and use sample records. Stop with the prototype and check results ready for my review. Ask before connecting accounts, changing real records, or deploying.
```

3. Open the running app and check that it counts those orders correctly. Read the agent's check results and note any checks it could not run.
4. Ask for a paid-order total instead. Check that the label changes, the total becomes one, and the draft remains excluded. Review the code changes with the agent.
