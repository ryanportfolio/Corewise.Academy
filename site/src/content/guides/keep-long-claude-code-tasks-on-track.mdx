<p class="lede">A long coding task can lose a requirement when you add a correction, or end with a summary that leaves the next step undone. Keep the current plan in a file, state which work may continue, and ask for a report that separates finished work from decisions waiting on you.</p>

Claude Code educator Duncan Rogoff demonstrates these habits in [How Anthropic Engineers Actually Use Claude Opus 5.5](https://www.youtube.com/watch?v=WKVcnfE_9Kw). His walkthrough draws on Addy Osmani's [Anthropic playbook](https://claude.dev/blog/getting-the-most-out-of-opus-5-5/). This guide applies their advice to an active coding task. For the initial request, start with [Give your coding agent a finish line](/guides/give-your-coding-agent-a-finish-line/).

## <span class="sec-no">01</span>Correct the active task

In Claude Code, type a follow-up and press Enter while the agent works. The playbook documents this way to [add a requirement mid-run](https://claude.dev/blog/getting-the-most-out-of-opus-5-5/#add-to-a-running-task); Rogoff demonstrates the idea at [3:37](https://www.youtube.com/watch?v=WKVcnfE_9Kw&t=217s).

Make the relationship to the original request explicit. This original follow-up adds a compatibility requirement:

```text
Continue the client migration. Keep the old endpoint names as aliases because existing callers still use them. Add tests that call those old names and update TASKS.md before continuing. The requested result is still a local patch ready for review.
```

Check that the next update includes the correction. If the new requirement conflicts with work already done, ask the agent to identify the affected files before proceeding.

## <span class="sec-no">02</span>Save progress with evidence

Rogoff recommends [a task list saved in a file](https://www.youtube.com/watch?v=WKVcnfE_9Kw&t=385s). The playbook names `TASKS.md`: a file remains available when Claude Code summarizes older conversation turns. Ask the agent to update the file as it works and reread it when resuming.

Our recommendation is to record evidence beside each completed item:

| Item | Record in the task file |
| --- | --- |
| Code changed | Affected paths and the requirement addressed |
| Check completed | Command or observed behavior, plus its result |
| Check blocked | What could not run and what access or input is missing |
| New requirement | The correction and the work it affects |

A checked box is a progress claim. Compare it with the files and check output. [Guardrails for hours-long agent runs](/guides/guardrails-for-long-runs/) covers saved context and fresh review in more depth.

## <span class="sec-no">03</span>Name the stops you want

The playbook recommends a short `CLAUDE.md` rule to prevent status reports from ending work that can continue. Keep permission prompts enabled for destructive commands. Rogoff also makes the boundary explicit:

<PullQuote
  quote="stop and ask only when you can't continue without me"
  creator="Duncan Rogoff"
  video="How Anthropic Engineers Actually Use Claude Opus 5.5"
  href="https://www.youtube.com/watch?v=WKVcnfE_9Kw"
  timestamp="5:40"
/>

He also names destructive actions and changes outside the repository as reasons to ask. This original rule keeps those limits and specifies the final report:

```text
Continue reversible work already covered by my request. Give progress updates while taking the next available action. Keep TASKS.md current, including corrections, completed checks, and blocked checks.

Ask when a missing decision prevents progress. Ask before deleting data, force-pushing, changing another repository, merging, or deploying. Preserve existing permission controls.

End with decisions needed from me, changes made, checks and their results, and anything unverified. Link the relevant files or evidence.
```

Put lasting project rules in `CLAUDE.md` and task-specific requirements in the request or task file. [Trim the instructions your model outgrew](/guides/trim-the-instructions-your-model-outgrew/) explains how to test instruction changes while keeping fixed requirements.

## <span class="sec-no">04</span>Check the remote handoff

A remote session needs the task, access, and checks required to finish it. Developer Theo adds a worked example in [Getting the most out of Opus 5.5](https://www.youtube.com/watch?v=ejjBbaq9RmY), his commentary on the same Anthropic playbook. He [moves a coding task to another computer](https://www.youtube.com/watch?v=ejjBbaq9RmY&t=318s) so browser automation can run without interrupting his laptop use.

His request names what the agent may do and when it should ask for help. For your own handoff, specify:

| Handoff detail | What to name |
| --- | --- |
| Destination | The machine, repository, branch, and approved connection method |
| Required access | Which configuration or credentials may be transferred, and where |
| Working environment | The runtime, test commands, and browser access to verify |
| Local limits | Whether the agent may open windows or control your current machine |
| Blocker | Ask if the destination or required tools fail, before choosing a different setup |

Theo [explicitly permits the configuration transfer](https://www.youtube.com/watch?v=ejjBbaq9RmY&t=378s) and [invites questions if the move fails](https://www.youtube.com/watch?v=ejjBbaq9RmY&t=482s). Keep that permission specific to the destination and task. [Assume your agent uses every tool it has](/guides/assume-your-agent-uses-every-tool-it-has/) covers how available tools affect those limits.

Check that implementation continues after setup. Theo discovers that the [new session stopped after phase zero](https://www.youtube.com/watch?v=ejjBbaq9RmY&t=564s), despite receiving a plan with later phases. Our recommendation is to record setup and implementation separately in `TASKS.md`, then confirm that the receiving session has the full finish condition and approval boundaries.

## <span class="sec-no">05</span>Avoid max effort by default

Theo recommends high or xhigh for Opus 5.5 and [warns against max effort](https://www.youtube.com/watch?v=ejjBbaq9RmY&t=777s). In his Skatebench comparison, max used far more tokens and time for a small accuracy gain:

| Reported result | xhigh | max |
| --- | --- | --- |
| Average tokens per response | 338 | About 5,000 |
| Average response time | 6 seconds | 50 seconds |
| Accuracy | 78% | 79% |

These are Theo's reported results on one benchmark. They support trying high or xhigh first; they do not establish that max is never useful. He [uses either high or xhigh in his own work](https://www.youtube.com/watch?v=ejjBbaq9RmY&t=869s). Compare effort settings on your task using the same completion check, and record quality, time, and token use. [Recheck your model choices each release](/guides/recheck-your-model-choices-each-release/) covers that comparison.

For other ways to reduce token use during long runs, use our [practical token-saving guide at savetokens.tips](https://savetokens.tips/guide). It covers shorter replies, scoped file reads, command-output filtering, and model routing.

## <span class="sec-no">06</span>Ask what could break

The playbook recommends reading what Claude needs from you before the rest of its final report. Resolve that decision, then compare the claimed result with the checks you requested.

Theo adds a useful question when returning to an old task: [what are the risks of merging this code today?](https://www.youtube.com/watch?v=ejjBbaq9RmY&t=1314s) Ask for the failure and its evidence. This original follow-up turns the answer into a review request:

```text
What could break if we merged this change today? For each risk, name the affected behavior, the evidence, and the check that would confirm or rule it out. Separate confirmed problems from unverified concerns. Say which checks could not run and what they need. This is a review request; do not merge.
```

Give the reviewer the tools needed to test those concerns. Theo [names missing hardware, environment variables, and subjective judgments](https://www.youtube.com/watch?v=ejjBbaq9RmY&t=1479s) as reasons a claim may remain unverified. Anthropic's [verification guidance](https://code.claude.com/docs/en/best-practices#give-claude-a-way-to-verify-its-work) recommends checks that return observable results, such as tests or screenshots.

For a large audit, request the division of work explicitly. Theo [reports that permission to use subagents can still leave the work unsplit](https://www.youtube.com/watch?v=ejjBbaq9RmY&t=1242s). Name the separate areas to review and require evidence from each. [Split big AI tasks into steps and checks](/guides/split-big-ai-tasks-into-steps-and-checks/) covers that division of work.

A second model can provide another review. Theo [finds value in switching model families](https://www.youtube.com/watch?v=ejjBbaq9RmY&t=1350s), while acknowledging that reviewers also report problems that do not matter. Treat each finding as a claim to verify against the code and a reproducible failure. Extra reviewers do not establish correctness by agreeing.

<Exercise>
1. Choose a local coding task with a check you can run. State the requested result, approval boundaries, and instruction to keep `TASKS.md` current.
2. While the agent works, add one relevant compatibility requirement. Check that the file and planned verification reflect it.
3. Read the final report's blocked and unverified items first. Ask what could break if merged today, then compare one claimed result or risk against the changed code and check output. Record any mismatch before approving the result.
</Exercise>
