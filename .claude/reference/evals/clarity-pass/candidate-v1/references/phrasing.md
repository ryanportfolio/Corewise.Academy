# Phrasing standard

These pairs establish the editorial standard. They are examples, not banned phrases or instructions to make every sentence look alike. Keep accurate technical terms, qualifications, and the writer's voice.

| Rejected wording | Direct version | Reason |
| --- | --- | --- |
| Questions can expose omissions | Ask the agent to question you about requirements you have not specified | The original names a general benefit without saying who should ask or what is missing. In a paragraph already recommending an interview, cut it instead of repeating the advice. |
| Give a business concept the same name in the conversation, requirements, interface, and code | If the people handling orders call an order "accepted," use that name in the app and code | The example names the thing and the action without making the reader translate "business concept." |

Retain clear writing even when it contains a technical term: "An idempotent request can be repeated without creating a second order." The definition makes the term useful. Retain consequential limits such as "This comparison covers one project; it does not establish which setting will work best for yours." Never change exact quotations or code to match the house voice.

Understanding what a sentence probably means is a lower standard than accepting it for publication. Prefer a direct action or explanation when it preserves the meaning. Do not manufacture edits to meet a quota.
